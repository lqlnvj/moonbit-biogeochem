# Marine biogeochemical engine acceptance hardening design

## Goal

Strengthen `moonbit-biogeochem` as a reusable marine biogeochemical simulation
library by adding production-grade trajectory analysis, scenario validation,
and water-column diagnostics; provide reproducible benchmark evidence and
boundary tests; modernize the repository README and CI; and keep the proposal
document unchanged.

## Non-goals

- No edit to `OSC2026_Hackathon_Proposal.md`.
- No Gitlink operation, GitHub push, Mooncakes publish, token configuration, or
  remote workflow dispatch.
- No new external MoonBit dependency unless the current toolchain proves an
  existing dependency is required and the dependency is explicitly approved.
- No artificial source padding, synthetic benchmark numbers, or claims based
  on test lines counted as production implementation.
- No breaking change to the existing public constructors and solver entry
  points.

## Baseline and success criteria

The baseline on 2026-08-24 is MoonBit 0.10.9, `moon check` exit 0, and 40/40
tests passing. The repository currently contains 4,449 physical production
`.mbt` lines and 613 physical test `.mbt` lines. The implementation must:

1. exceed 5,000 physical production `.mbt` lines using meaningful reusable
   functionality;
2. keep production and test line counts separate in the measurement output;
3. add boundary tests for invalid dimensions, empty data, non-monotonic time,
   non-finite values, zero/negative numerical parameters, and transport
   stability limits;
4. provide benchmark output generated by a deterministic MoonBit workload and
   a local timing command, with machine/date context and no fabricated target;
5. pass `moon check --deny-warn`, `moon test --deny-warn`, `moon fmt --check`,
   `moon info`, a release CLI run, and the repository CI command set locally;
6. keep the README focused on users, APIs, reproducibility, license, and
   development, with no applicant/acceptance/sole-contributor wording.

## Architecture

The design keeps the existing package graph and adds narrow capabilities at
the package that owns the relevant data:

```text
types ──► core ──► solver ──► models
  │         │         │         │
  └─────────┴─────────┴──────► analysis
                         │
                         └────► extensions ──► CLI benchmark/demo
```

### 1. Solver trajectory integrity

The solver package remains the owner of `Trajectory` and `TrajectoryPoint`.
Additive validation APIs will check variable-name uniqueness, point vector
dimensions, finite time/value data, strictly increasing timestamps, and
non-negative finite step sizes. Existing `append` and `get_time_series` calls
remain source-compatible; checked variants return `Result[..., String]` for
callers that need failure details. Empty trajectories and missing variables
must return errors rather than indexing an empty array.

### 2. Analysis metrics and scenario quality

The analysis package will expose small, composable value types for:

- descriptive series statistics: count, minimum, maximum, mean, trapezoidal
  integral, finite status, and linear trend;
- threshold crossings with direction and interpolated crossing time;
- trajectory-wide summaries including duration and observed time-step range;
- ecological quality checks for non-negative concentrations, configured state
  bounds, parameter bounds, finite values, and solver step-size settings.

Metrics operate on supplied timestamps and values or on an existing trajectory.
They do not silently repair data. Invalid input produces a descriptive error;
valid but scientifically meaningful zero-valued series produce a valid result.
The report type separates errors that make a scenario invalid from warnings
that are useful for review.

### 3. Water-column diagnostics

The extensions package will add checked construction/validation helpers and a
diagnostics value type for `WaterColumn1D`. The diagnostics cover layer count,
depth spacing, state-vector shape, finite/non-negative concentrations, total
inventory, boundary flux balance, and an explicit diffusion/advection CFL
limit. The existing no-error constructor and step function stay available for
compatibility, while new checked functions allow production callers and the
CLI to reject invalid setups before simulation.

### 4. Reproducible benchmark harness

Add a native `cmd/benchmark` executable that runs fixed NPZD and coupled
NPZD-carbon workloads for a configurable repeat count, prints a stable CSV
header, and reports workload sizes, trajectory points, final diagnostics, and
the toolchain version supplied by the runner. A PowerShell helper will run the
release binary repeatedly and calculate wall-clock summaries. The checked-in
benchmark report will contain only values produced by that helper, with the
machine/date and exact command recorded. Timing is evidence for comparison,
not a portability guarantee.

## Error handling

- Public checked APIs use `Result[T, String]`, matching the existing project
  style and avoiding a new error dependency.
- Error messages identify the invalid field and value class, for example
  `trajectory time must be strictly increasing` or
  `water column requires at least one layer`.
- Functions that accept arrays must validate length before indexing.
- Numerical routines must reject or report non-finite values and non-positive
  denominators where the operation is undefined.
- Diagnostics never mutate input trajectories or state vectors.
- Existing compatibility APIs may retain their current value-returning shape,
  but their implementation must delegate to safe helpers where possible.

## Testing strategy

Implementation follows red-green-refactor for each public behavior:

1. add a focused black-box or white-box test;
2. run the narrow test and observe the expected failure;
3. implement the smallest behavior that passes;
4. run the focused test and the package suite;
5. refactor only while the suite remains green.

Coverage will include:

- empty and one-point trajectories;
- duplicate variable names and mismatched point dimensions;
- non-monotonic and repeated timestamps;
- NaN/infinite values where supported by the current MoonBit runtime;
- constant, negative, all-zero, and threshold-touching series;
- zero, negative, and very large step sizes;
- empty parameter maps and out-of-bound parameters;
- zero-layer, one-layer, uneven-state, and non-finite water columns;
- diffusion/advection stability at, below, and above the CFL limit;
- deterministic benchmark output and non-empty CLI reports;
- regression checks that existing models and solvers retain their current
  successful behavior.

## CI and documentation

The CI workflow will use the official latest stable installation scripts on
Linux, macOS, and Windows. It will run `moon version --all`, dependency
update, formatting check, all-target check/test with warnings denied, native
test coverage where supported, `moon info`, and a generated-interface diff
check. Platform-specific native prerequisites will be installed only where
needed. The workflow will not publish packages or access secrets.

The README will be reorganized into: overview, capabilities, architecture,
package map, quick start, library example, validation/benchmark commands,
testing and development, compatibility, license, and contribution guidance.
It will report source metrics only through the reproducible measurement command
and will not copy proposal-only figures or internal acceptance language.
